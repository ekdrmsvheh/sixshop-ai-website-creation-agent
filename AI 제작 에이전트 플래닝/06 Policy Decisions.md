# 06 Policy Decisions

## 목적
랜딩에서 시안 생성, 가입 후 온보딩, 에디터 전환까지 이어지는 AI 웹사이트 제작 플로우의 UX, 카피, 로직 결정 사항을 기록한다.

이 문서는 대화와 시안 검토를 거치며 계속 업데이트한다. 결정된 내용과 열린 이슈를 분리해, 이후 제품/디자인/개발 논의에서 기준점으로 사용한다.

`02 UX Flow`는 지도처럼 짧게 유지하고, 특정 단계의 상세 정책은 별도 문서로 분리한다. `06 Policy Decisions`는 모든 디테일을 길게 누적하기보다, 중요한 결정과 연결 문서를 찾는 기준점으로 사용한다.

## 1. 랜딩 → 로그인 전환

랜딩에는 5개의 제작 시작 유형이 있다.

| 유형 | 입력 방식 | 로그인 전환 조건 |
|---|---|---|
| 아이디어 설명하기 | 프롬프트 입력, 파일 첨부 가능 | 텍스트 입력 후 버튼 클릭 여부 확인 후 전환 |
| HTML | 코드 입력 또는 코드 파일 첨부 | 입력/버튼 클릭 이후 전환 |
| URL | 사이트 클론용 URL 입력 | 입력/버튼 클릭 이후 전환 |
| Figma | URL 입력, 계정 연동 버튼 | 입력/버튼 클릭 이후 전환 |
| 이미지 | 이미지 파일 첨부 | 입력/버튼 클릭 이후 전환 |

랜딩은 로그인 상태를 알 수 없으므로, 어느 제작 시작 유형이든 입력 또는 버튼 클릭 같은 확정 액션 이후에는 PRO 로그인 모달이 노출된다.

아이디어 설명하기 유형에만 "텍스트 입력 후 버튼 클릭?" 단계가 추가된다.

| 조건 | 동작 |
|---|---|
| Yes, 글자 수 제한 이내 | PRO 로그인 모달 즉시 노출 |
| Yes, 글자 수 제한 초과 | 안내 문구 노출 후 PRO 로그인 모달 노출 |
| No | 입력 대기 상태 유지, 로그인 모달 미노출 |

PRO 로그인 모달에서 기존 사용자는 단순 로그인 클릭으로, 신규 사용자는 회원가입 버튼 클릭 후 PRO 회원가입 모달로 전환해 로그인/회원가입을 완료한다. 완료 후에는 스토어 매니저 > 계정의 기본 스토어로 진입한다.

랜딩 프롬프트를 거쳐 온 사용자는 테마 보유 여부와 상관없이 바로 "프롬프트+템플릿 단독 페이지"로 진입한다.

## 2. 라우터 제약 → 선택형 UX

현재 스토어 매니저와 에디터 프론트엔드에는 URL 라우터가 없다. 화면 전환을 경로 기반으로 처리할 수 없으므로, 사용자가 자유 문장으로 무엇이든 요청하는 완전 자유 채팅 방식은 채택하기 어렵다.

이유는 자유 발화에서 매번 사용자의 의도를 해석해 어떤 화면과 상태로 이어질지 라우팅할 방법이 없기 때문이다.

따라서 이 플로우 전체는 미리 정의된 선택지, 버튼, 카드, 폼을 고르는 방식으로 설계한다.

| 분기점 | UX 방식 |
|---|---|
| 제작 시작 유형 5개 | 고정된 입력 유형 선택 |
| 시안 생성 후 후속 액션 4개 | 고정 액션 버튼 |
| 온보딩 체크리스트 항목 | 체크리스트 기반 CTA |
| 추가 정보 수집 | 폼 또는 선택지 |

유일한 자유 텍스트 입력은 최초 프롬프트와 시안 수정 요청 정도로 한정한다. 그 다음 단계는 항상 선택형으로 좁힌다.

## 3. 가입 후 온보딩 → 디자인 관리 구조

가입 후 첫 화면은 스토어 매니저 홈이다. 상태에 따라 두 가지로 나뉜다.

| 상태 | 화면 |
|---|---|
| PG 연동 전 | 빠른 시작을 위한 설정 가이드 체크리스트 |
| PG 연동 완료 후 | 운영 대시보드 |

PG 연동 전 체크리스트는 다음 순서로 구성된다.

1. 웹사이트 만들기: 템플릿 선택하기
2. 기본 정보 입력
3. 배송/환불 정책
4. 상품 1개 추가
5. 약관/필수 정보
6. 결제 서비스(PG) 연동
7. 도메인 연동

첫 항목인 "템플릿 선택하기" CTA가 시안 생성 플로우의 진입점이다.

채널 관리 > 웹사이트 > 디자인 화면은 선택한 템플릿 개수에 따라 3가지 상태를 갖는다.

| 템플릿 수 | 화면 상태 |
|---|---|
| 0개 | 게시 중인 디자인 없음. 안내 배너와 템플릿 그리드만 노출 |
| 1개 | 게시 중인 디자인 카드 노출. 디자인 보관함은 비어 있음 |
| 2개 이상 | 게시 중인 디자인 1개와 나머지 디자인 보관함 리스트 노출 |

랜딩 → 시안 대화 플로우의 도착지는 이 디자인 탭이다. 시안 결정 시 선택한 시안은 게시 중인 디자인으로, 생성 과정에서 나온 나머지 후보 시안들은 디자인 보관함으로 매핑되는 것이 자연스럽다.

단, 실제 연동 방식은 아직 미정이다.

랜딩 프롬프트로 시작한 사용자는 테마 보유 여부와 상관없이 바로 "프롬프트+템플릿 단독 페이지"로 진입한다. 랜딩에서 입력한 텍스트는 유지되지만, 파일 첨부와 Figma 계정 연동은 이 페이지에서 다시 해야 한다.

테마가 이미 있는 사용자는 이 절을 거치지 않고 온보딩 또는 운영 대시보드로 이동한다. 테마가 0개이고 랜딩 프롬프트로 오지 않은 사용자는 온보딩 화면에 동일한 프롬프트+템플릿 섹션을 별도로 제공한다.

## 4. 시안 생성

사용자가 랜딩에서 프롬프트를 입력하면 다음 순서로 진행한다.

| 단계 | 상태 | 설명 |
|---|---|---|
| 1 | 요약 | 사고 중 표시 후 AI가 사용자 입력을 요약한 문장을 타이핑 |
| 2 | 기본 정보 확인 안내 | 요약 완료 후 다시 사고 중 표시, 기본 정보 확인 안내 타이핑 |
| 3 | 작업 계획 폼 | 안내 문구 완료 후 인테이크 폼 등장 |
| 4 | 생성 및 생성 완료 | 폼 제출 후 스플릿 스크린으로 전환, 시안 4가지 생성 |

시안 생성 전 기본 정보 확인 단계의 상세 분기와 질문 정책은 [07 Basic Info Intake](./07%20Basic%20Info%20Intake.md)를 따른다.

요약 메시지 형식은 다음과 같다.

```text
말씀해주신 내용을 정리해봤어요.

"{사용자 요청}"

이 요청을 바탕으로 목적에 맞는 구조와 톤을 잡아서 메인 페이지부터 만들어볼 거에요.
제가 디자인 시안 4가지를 보여드리면, 마음에 드는 시안을 고르면 돼요.
```

기본 정보 확인 안내 문구는 다음과 같다.

```text
필요한 정보를 확인하고 시작할게요.
```

작업 계획 폼은 대화 흐름을 유지한 채 이어지는 형태로 노출한다. 폼 안의 세부 질문, 목적별 프리셋, 직접 입력 정책은 [07 Basic Info Intake](./07%20Basic%20Info%20Intake.md)를 기준으로 한다.

구현 메모:

- 두 타이핑 시퀀스는 중첩 `setTimeout`이 아니라 독립적인 최상위 스케줄로 실행되어야 한다.
- 요약 → 점 표시 → 안내 → 폼 체인이 막히지 않도록 한다.
- 로그, 즉 AI 작업 로그 창이 열리는 순간 "테마 생성" 개념을 갖는다.
- 이때 테마는 임시로 생성되지만 디자인 보관함에는 반영되지 않는다.

## 5. 시안 생성 후 후속 액션

시안 결과와 함께 4가지 후속 액션을 항상 노출한다.

| 액션 | 설명 |
|---|---|
| 새로 만들기 | 처음부터 다시 시안을 생성 |
| 시안 수정 | 생성된 시안에 대해 대화로 수정 요청 |
| 이 시안으로 생성하기 | 해당 시안을 기반으로 에디터 전환 후 실제 페이지 생성 |
| 템플릿 중에 고르기 | AI 추천 템플릿 중 하나를 선택해 템플릿 기반으로 시작 |

시안 수정은 선택한 시안 단위로 반영한다. 예시는 톤 조정, 섹션 추가/제거 등이다.

템플릿 중에 고르기는 다음 흐름을 목표로 한다.

1. AI가 추천한 템플릿 중 하나를 클릭한다.
2. 템플릿 리뷰를 노출해 시안 퀄리티와 실제 템플릿의 차이를 명확히 한다.
3. "이 템플릿으로 시작하기"를 클릭한다.
4. 해당 템플릿으로 테마가 생성되며 에디터로 전환된다.

## 6. 시안 결정 → 에디터 전환 → 페이지 생성

"이 시안으로 생성하기" 또는 템플릿 선택을 거쳐 테마가 생성되면 에디터로 전환된다.

전환 직후에는 다음 중 하나의 상태로 시작한다.

| 상태 | 설명 |
|---|---|
| AI 작업 로그 창 비어 있음 | 아직 생성 로그가 없는 상태 |
| 생성 중인 페이지 선택됨 | 페이지 생성 진행 상태를 바로 보여주는 상태 |

생성이 완료되면 다음이 함께 일어난다.

1. AI 작업 로그 창에 완료 표시
2. 스낵바 안내
3. 생성된 페이지 표시

## 7. 기존 사용자 — 디자인 페이지 진입

채널 관리 > 웹사이트 > 디자인 페이지에 진입한 기존 사용자는 두 상태로 나뉜다.

| 상태 | 화면 |
|---|---|
| 디자인 있음 | 프롬프트 / 템플릿 2개 CTA를 나란히 제공 |
| 디자인 없음 | 프롬프트 섹션 + 템플릿 목록 섹션을 페이지의 절반 이상으로 노출 |

디자인이 있는 상태에서는 에디터 진입 시 AI 작업 로그 창이 기본으로 열려 있지 않고, AI 버튼을 눌러야 노출된다.

다만 다음 케이스에서는 진입 즉시 노출하는 방식도 고려 중이다.

- 기능 출시 후 최초 1회
- 템플릿으로 시작한 사용자
- AI 제작 배너를 클릭해 진입한 사용자

디자인이 없는 상태의 흐름은 "프롬프트+템플릿 단독 페이지"와 동일하게 설계한다.

## 8. 채팅 응답 UX 규칙

사용자가 새 입력을 보내면 해당 턴이 화면 상단으로 올라와 포커스된다. 이전 턴은 스크롤 아래로 밀린다.

AI 응답은 한 번에 나타나지 않는다. 다음 순서로 노출한다.

1. 타이핑 인디케이터: 점 3개, 바운스, 약 1.2초
2. 글자 단위 순차 출력: 약 40ms/글자
3. 각 글자는 opacity 0 → 1로 페이드
4. 글자 이동 애니메이션은 사용하지 않음

## 9. 컴포넌트 네이밍 — 채팅 입력 / 피드백 UI

Chat Layout에는 사용자 자유 입력을 받는 `ChatComposerInput`과, AI가 다음 단계 진행을 위해 정해진 선택/입력을 요청하는 `FeedbackPrompt`가 함께 존재한다.

출시 버전에서는 라우터 제약과 플로우 안정성을 우선해 `FeedbackPrompt`만 노출한다. 추후에는 `ChatComposerInput`이 기본 입력 컴포넌트가 되고, 사용자의 자유 입력만으로 다음 상태를 안정적으로 판단하기 어려운 분기점에서 `FeedbackPrompt`를 함께 사용한다.

| 시점 | 기본 노출 컴포넌트 | 사용 기준 |
|---|---|---|
| 출시 버전 | `FeedbackPrompt` | 선택형 UX로 플로우를 제어해야 하는 구간에서 사용 |
| 향후 버전 | `ChatComposerInput` | 사용자가 자유롭게 요청, 질문, 수정 의견을 입력하는 기본 채팅 입력으로 사용 |
| 향후 버전의 보조 패턴 | `FeedbackPrompt` | 확인, 승인, 선택, 구조화된 입력이 필요한 분기점에서 사용 |

### Chat Composer Input

`ChatComposerInput`은 Chat Layout 하단에 고정되어 사용자의 자유 텍스트 입력과 파일 첨부를 받는 기본 입력 컴포넌트다.

주로 사용자가 스타일, 레이아웃, 콘텐츠, 수정 방향 등을 자유롭게 설명해야 할 때 사용한다. AI 제작 플로우가 자유 채팅 기반으로 확장된 이후에는 사용자의 기본 발화 진입점이 된다.

정의문:

```text
Chat Composer Input은 AI 제작 플로우에서 사용자가 자유 텍스트와 첨부 파일로 요청, 질문, 수정 의견을 입력하는 기본 채팅 입력 컴포넌트다.
```

사용 기준:

| 상황 | 사용 여부 |
|---|---|
| 최초 프롬프트 입력 | 사용 가능 |
| 시안 수정 요청 | 사용 가능 |
| 일반 질문 / 추가 요청 | 향후 사용 |
| 명확한 화면 전환이 필요한 분기 | 단독 사용 지양, `FeedbackPrompt`와 함께 사용 |
| 승인 / 선택 / 폼 입력이 필요한 구간 | `FeedbackPrompt` 사용 |

### Feedback Prompt

Astryx의 `ChatComposerDrawer`는 식스샵 프로에서는 구조명인 `Drawer`보다 역할 중심으로 정의하는 것이 적합하다.

식스샵 프로의 핵심 제약은 "완전 자유 채팅을 라우팅하기 어렵다"는 점이고, 이 UI의 본질은 AI가 다음 단계로 진행하기 전에 사용자에게 정해진 선택 또는 입력을 요청하는 것이다.

따라서 피드백 UI의 상위 개념은 `FeedbackPrompt`로 정의한다.

| 레벨 | 추천 이름 | 역할 |
|---|---|---|
| 패턴 / 상위 개념 | `FeedbackPrompt` | AI가 다음 진행을 위해 확인, 선택, 입력을 요청하는 인터랙션 |
| 폼 변형 | `FeedbackForm` | 브랜드명, 톤, 필수 요소처럼 구조화된 정보를 받는 형태 |
| 선택지 변형 | `FeedbackOptions` | Yes/No, 시안 선택, 후속 액션처럼 고정 선택지를 고르는 형태 |
| 레이아웃 변형 | `BottomDrawer` / `ComposerDrawer` | 필요할 때만 형태 이름으로 사용하는 하위 구현 |

정의문:

```text
Feedback Prompt는 AI 제작 플로우에서 다음 단계 진행을 위해 사용자에게 고정된 선택지 또는 구조화된 입력을 요청하는 컴포넌트다. 라우터 제약으로 인해 자유 채팅 대신 선택형 UX를 제공해야 하는 분기점에서 사용한다.
```

현재 이미지 기준 매핑:

| 예시 | 컴포넌트명 |
|---|---|
| Yes / No / Don't ask again 선택 UI | `FeedbackPrompt.Options` 또는 `FeedbackOptions` |
| 작업 계획 입력 폼 | `FeedbackPrompt.Form` 또는 `FeedbackForm` |
